# Матрица доступа — вариант 7

Обозначения: **C** — Create, **R** — Read, **U** — Update, **—** — нет доступа.

## Исходная схема (2 отношения)

### `task` (Отношение 1)

- Составной первичный ключ: `(project_code, task_name)`.
- Альтернативный ключ AK1: `(project_name, task_name)`.
- `executor_fio` — внешний ключ на `employee.fio`.
- `real_date` — допускает NULL («если есть»).

| Атрибут | Сотрудник | Руководитель |
| --- | --- | --- |
| `project_code` | — | R |
| `project_name` | R | R |
| `task_name` | R | R |
| `executor_fio` | R | R |
| `workload_hours` | R | R |
| `plan_date` | R | R |
| `real_date` | R, U | R, U |
| `description` | R | R |
| `manager_approved` | — | R, U |

### `employee` (Отношение 2)

- Первичный ключ: `fio`.
- `manages_project_code` — код проекта, которым руководит сотрудник (NULL, если не руководит).

| Атрибут | Сотрудник | Руководитель |
| --- | --- | --- |
| все атрибуты | — | — |

Прямое чтение таблицы сотрудников в задании не предусмотрено. «Кто я»
определяется сессионной переменной `app.current_user` (ФИО сотрудника),
которую выставляет управляющий сценарий.

## Горизонтальные ограничения

- Сотрудник видит задачи проектов, на которых он работает (как исполнитель
  или как руководитель проекта).
- Сотрудник изменяет `real_date` только в задачах, где он является
  исполнителем.
- Руководитель видит все данные по своему проекту (все задачи и
  исполнители) и корректирует `manager_approved` только в его задачах.

## Реализованная матрица

| Ограничение | Средство | Результат |
| --- | --- | --- |
| Сотрудник: чтение названий проектов своего участия | `SELECT project_name FROM task` + RLS `employee_select_policy` | Реализовано |
| Сотрудник: задачи без `project_code` и `manager_approved` | `GRANT SELECT (перечень столбцов)` | Реализовано |
| Сотрудник: видит только свои проекты | RLS `employee_select_policy` | Реализовано |
| Сотрудник: изменение `real_date` только в своих задачах | `GRANT UPDATE (real_date)` + RLS `employee_update_policy` | Реализовано |
| Руководитель: полный набор полей задач своего проекта | `GRANT SELECT (все столбцы)` + RLS `manager_select_policy` | Реализовано |
| Руководитель: изменение `manager_approved` в своём проекте | `GRANT UPDATE (manager_approved)` + RLS `manager_update_policy` | Реализовано |
| «Сотрудник, руководитель и исполнитель одновременно» | объединение политик `employee_*` и `manager_*` | Реализовано |

## Особенности, не выражаемые стандартными средствами

- `employee.manages_project_code` не объявлен внешним ключом: в отношении
  задач `project_code` не уникален (у проекта много задач), а отдельной
  таблицы проектов по заданию нет. Целостность кода проекта на уровне FK
  не задаётся; семантика «руководит проектом» обеспечивается политиками RLS.
- Ограничение «сотрудник видит только названия проектов, на которых
  работает» реализовано на уровне строк RLS; полного отдельного списка
  всех проектов без справочника не предусмотрено.
