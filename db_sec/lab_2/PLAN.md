# Лабораторная работа №2 — Организация уровневого доступа к данным

Статус: выбран вариант 1 (рецепты и аптеки).

## Вариант 1
Отношение 1 — рецепты: номер рецепта (PK), код заболевания,
ФИО пациента (AK1), дата выписки (AK1), ФИО врача,
срок действия в днях (если есть), наименование лекарства,
код лекарства, признак использования рецепта, номер аптеки (FK).
Отношение 2 — аптеки: номер аптеки (PK), ФИО провизора (AK1),
город аптеки (AK2), адрес аптеки (AK2).

Права доступа:
- врач: видит все данные рецептов, кроме ФИО пациента и кода
  заболевания; эти два поля видит только для рецептов, которые
  выписал сам; может добавлять рецепты и изменять срок действия
  в своих рецептах.
- провизор: видит все данные рецептов, кроме ФИО врача и кода
  заболевания; может изменять признак использования и номер
  аптеки только для ещё действующих на момент изменения рецептов.

## Порядок выполнения (по методичке)
1. Реализовать ограничение целостности: признак использования рецепта может меняться только из `false` в `true`.
2. Создать представления, полностью реализующие права доступа из первой работы.
3. Выдать пользователям права только на представления.
4. Обеспечить и протестировать обновляемость представлений через `INSTEAD OF` триггеры.
5. Сравнить представления с встроенными средствами из первой работы.
6. Реализовать аудит манипуляций с базовой таблицей.
7. Оценить ограничения и операционные характеристики лог-контента.

## Структура файлов
- `schema.sql` — базовые таблицы.
- `data.sql` — тестовые данные.
- `views.sql` — представления и `INSTEAD OF` триггеры.
- `integrity.sql` — триггер ограничения целостности.
- `access.sql` — роли, учётные записи, права на представления.
- `audit.sql` — таблица лога, триггер аудита.
- `verify_access.sql` — ручной сценарий проверки.
- `lab2.py` — автоматический запуск и демонстрация.
