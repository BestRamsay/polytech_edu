# Работа № 2. Организация уровневого доступа к данным

## Общие сведения

**Цель работы** — получение навыков обработки событий и гранулирования доступа при работе с СУБД.

## Управление событиями в СУБД

В том случае, когда декларативных ограничений целостности недостаточно для задания ограничений целостности, используются **триггеры**.

**Триггер** — это процедура, хранимая в базе данных и вызываемая автоматически при возникновении каких-либо событий.

### Триггеры в PostgreSQL

В PostgreSQL код триггера не «вкладывается» в его тело (как в других СУБД и в стандарте SQL), а используется **триггерная функция**. При этом одна и та же триггерная функция может быть использована для нескольких триггеров.

Пример триггерной функции и триггера:

```sql
CREATE OR REPLACE FUNCTION function_usage_update()
RETURNS TRIGGER LANGUAGE PLPGSQL
AS
$$
BEGIN
  IF OLD.usage = true AND NEW.usage = false THEN
    RAISE EXCEPTION 'UNABLE TO UPDATE ''true'' to ''false''';
  ELSE
    RETURN NEW;
  END IF;
END;
$$;

CREATE OR REPLACE TRIGGER usage_update
BEFORE UPDATE ON prescription
FOR EACH STATEMENT EXECUTE PROCEDURE function_usage_update();
```

### Порядок срабатывания триггеров

- При создании нескольких триггеров, связанных с одним и тем же событием, они вызываются в **алфавитном порядке по имени триггера**.
- Для триггеров `BEFORE` и `INSTEAD OF` потенциально изменённая строка, возвращаемая одним триггером, становится входящей строкой для следующего триггера.
- Если любой из триггеров `BEFORE` или `INSTEAD OF` возвращает `NULL`, операция для этой строки прекращается и последующие триггеры (для этой строки) не срабатывают.

### Применение триггеров в задачах ИБ

Триггеры в задачах информационной безопасности баз данных могут широко использоваться как средство обработки событий:

- обновления представлений;
- создания систем пользовательского аудита;
- контроля происходящего в СУБД.

## Уровневый доступ к данным

Пользовательский слой доступа к данным в реляционных СУБД строится при помощи **представлений**, **функций** и **процедур**.

### Представления

**Представление (VIEW)** — это именованное реляционное выражение. SQL-запрос на выборку данных, который представляется пользователю и позволяет манипулировать собой как обычным отношением.

Использование представлений основано на реляционном свойстве **замкнутости**, говорящем, что результатом выполнения реляционной операции над отношением является реляционное отношение.

Выражение реляционной алгебры, формирующее представление, называется **выражением, определяющим представление**, и не вычисляется в момент создания, а запоминается системой в качестве объекта сервера (базы данных) под указанным именем.

**Метаданные представления:**
- имя в каталоге сервера;
- способ получения кортежей представления.

Это всё, что хранится физически. Значением представления будет результат выполнения его определяющего выражения над базовыми таблицами реляционного сервера.

### Назначение представлений

1. Хранение типовых пользовательских запросов (и, таким образом, оптимизированных представлений).
2. Разграничение доступа к данным.
3. Обеспечение логической независимости данных.

Создание представлений определено в стандарте SQL и производится оператором `CREATE VIEW` с рядом параметров.

### Виды представлений

Виды представлений основаны на различиях определяющих их реляционных выражений. В этом ключе представления разделяются по входящим в определяющие их выражения реляционным операциям и обновляемости:

1. **Горизонтальное представление** — основано на реляционной операции сокращения (фильтрация строк).
2. **Вертикальное представление** — основано на реляционной операции проекции (выборка столбцов).
3. **Сгруппированные представления** — определяющее выражение содержит различные методы агрегации (группировки).
4. **Объединённые представления** — построенные на более чем одном базовом источнике (базовом отношении или другом представлении).

### Обновляемость представлений

Сложности в работе с представлениями связаны с необходимостью обновления этих структур данных. Если конечный пользователь видит представление и воспринимает его как базовый набор данных, то вставку и изменение данных он также должен осуществлять через представление. Однако этот процесс может вызвать сложности для сгруппированных или объединённых объектов.

Стандарт SQL предусматривает ряд ограничений на обновление представлений. В частности, стандарт SQL-2 вводит понятия:

- принципиальной применимости операций обновления;
- простой применимости операций обновления;
- применимости операций вставки.

Также включает набор дополнительных правил, устанавливающих восприимчивость разных языковых конструкций к операциям обновления и вставки. В ряде коммерческих СУБД эти требования ещё более смягчены и расширены для более широкого класса представлений, однако полный перечень ограничений обновляемости является различным для разных производителей.

Обновление представлений, не подлежащих простым обновлениям при помощи операторов `UPDATE` и `INSERT`, тем не менее можно производить при помощи **триггеров**. Триггер перехватывает запрос на обновление данных и реализует вместо него те операции над заданными таблицами, которые необходимы в каждом конкретном случае. Таким же образом в триггере `INSTEAD OF` можно:

- заполнять невидимые пользователю поля таблиц фиксированными или сгенерированными значениями;
- проверять корректность пользовательских данных.

Пример триггера на обновление представления:

```sql
CREATE OR REPLACE FUNCTION update_info()
RETURNS TRIGGER LANGUAGE PLPGSQL AS
$$
BEGIN
  IF (OLD.validity != NEW.validity) THEN
    UPDATE prescription SET validity = NEW.validity
    WHERE id_prescription = OLD.id_prescription;
  ELSIF (OLD.usage != NEW.usage
         OR OLD.pharmacy_number != NEW.pharmacy_number) THEN
    UPDATE prescription SET usage = NEW.usage,
      pharmacy_number = NEW.pharmacy_number
    WHERE id_prescription = OLD.id_prescription;
  END IF;
  RETURN NEW;
END;
$$;

CREATE OR REPLACE TRIGGER trigger_update_info
INSTEAD OF UPDATE ON info
FOR EACH ROW EXECUTE PROCEDURE update_info();
```

### Представления в целях защиты информации

С целью защиты информации представления могут выполнять две функции:

1. **Сокрытие реальной структуры данных** — пользователь работает с упрощённой или видоизменённой моделью.
2. **Изоляция объектов и данных при разграничении прав доступа** — пользователю выдаются права не на таблицы, а на представления.

## Хранимые подпрограммы и процедуры

Языки доступа и манипулирования данными современных коммерческих СУБД, основанные на языке SQL (например, Transact-SQL, применяемый в MS SQL Server, или PL/SQL от Oracle), позволяют пользователям базы данных создавать свои процедуры и функции для обработки решений бизнес-логики напрямую в рамках реляционного сервера.

### Классификация подпрограмм

- **Многооператорные процедуры (Multi-statement Procedures)** — группы операторов SQL, которые могут выполняться совместно. Разработчику предоставляются операторы управления логикой исполнения, локальные переменные и средства обработки условий.
- **Хранимые подпрограммы и модули (Stored routines and modules)** — включают в себя процедуры, функции и модули, которые могут храниться в SQL-сервере.
- **Внешние подпрограммы (External routines)** — функции и процедуры, написанные на включающих языках третьего поколения (3GL), которые могут вызываться из операторов SQL.

Также необходимо помнить, что большинство крупных коммерческих (и не только) СУБД предлагают собственные расширения, сверх SQL/PSM.

### Пакет и подпрограмма

Полезно выделить два понятия:

- **Пакет (batch)** — последовательность инструкций языка.
- **Подпрограмма (routine)** — выделенная пользовательская процедура или функция. Подпрограммы являются именованными объектами базы данных, где хранятся в откомпилированном виде.

Пакет можно сохранить в рамках базы данных как процедуру или определяемую пользователем функцию.

### Применение хранимых процедур и функций

Хранимые процедуры и функции применяются:

- для авторизации доступа;
- для аудита базы данных и создания контрольных записей действий пользователей;
- для принудительного обеспечения целостности и выполнения правил модификации;
- для улучшения производительности повторяемых задач.

## Аудит действий пользователей

Приведём пример создания типа данных, таблицы логирования и триггера для пользовательского аудита при работе с данными на PL/SQL (PostgreSQL).

```sql
DROP TABLE IF EXISTS log_pharmacy;

CREATE TYPE act AS ENUM ('insert', 'update', 'delete');

CREATE TABLE log_pharmacy(
  id          SERIAL NOT NULL,
  username    VARCHAR(50) NOT NULL,
  action      act NOT NULL,
  change      text,
  changed_on  TIMESTAMP(6) NOT NULL
);

CREATE OR REPLACE FUNCTION audit()
RETURNS TRIGGER LANGUAGE PLPGSQL AS
$$
BEGIN
  IF (TG_OP = 'DELETE') THEN
    INSERT INTO log_pharmacy
      (username, action, change, changed_on)
    VALUES(current_user, 'delete',
      format('pharmacy_number: ''%s'';
             pharmacy_city: ''%s'';
             name_pharmacist: ''%s'';
             pharmacy_address: ''%s''',
        OLD.pharmacy_number, OLD.pharmacy_city,
        OLD.name_pharmacist, OLD.pharmacy_address),
      now());
    RETURN OLD;
  ELSIF (TG_OP = 'UPDATE') THEN
    INSERT INTO log_pharmacy
      (username, action, change, changed_on)
    VALUES(current_user, 'update',
      format('pharmacy_number: ''%s'' -> ''%s'';
             pharmacy_city: ''%s'' -> ''%s'';
             name_pharmacist: ''%s'' -> ''%s'';
             pharmacy_address: ''%s'' -> ''%s''',
        OLD.pharmacy_number, NEW.pharmacy_number,
        OLD.pharmacy_city, NEW.pharmacy_city,
        OLD.name_pharmacist, NEW.name_pharmacist,
        OLD.pharmacy_address, NEW.pharmacy_address),
      now());
    RETURN NEW;
  ELSIF (TG_OP = 'INSERT') THEN
    INSERT INTO log_pharmacy
      (username, action, change, changed_on)
    VALUES(current_user, 'insert',
      format('pharmacy_number: ''%s'';
             pharmacy_city: ''%s'';
             name_pharmacist: ''%s'';
             pharmacy_address: ''%s''',
        NEW.pharmacy_number, NEW.pharmacy_city,
        NEW.name_pharmacist, NEW.pharmacy_address),
      now());
    RETURN NEW;
  END IF;
  RETURN NULL;
END;
$$;

CREATE OR REPLACE TRIGGER emp_audit
AFTER INSERT OR UPDATE OR DELETE ON pharmacy
FOR EACH STATEMENT EXECUTE PROCEDURE audit();
```
